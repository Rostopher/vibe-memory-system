# Evolutionary Development

让功能增长与可修改性一起演进。遵循现有业务契约，按不确定性选择方法，
以证据决定结构调整。流程不绑定特定模型版本。

## 选择开发方式

| 情况 | 方式 | 要得到什么 |
|---|---|---|
| 技术、数据能力或总体方案不明确 | 隔离 demo、side project 或独立仓库 | 关键假设的验证证据 |
| 方向明确但局部行为未知 | `probe_<用途>`、最小复现或局部原型 | 可用于实现或定位的观察 |
| 需求和实现路径清楚 | 在既有模块直接实现 | 完整能力和相关验证 |

复杂程度和文件数量不直接决定是否 Explore。不要求每次新功能先建 demo，
也不要求每次修改先写测试文件。复用当前授权，不把阶段名称变成额外审批程序。

## Explore → Learn

在运行前明确本轮问题与足以支持判断的样本、条件或观察方法，规模与未知程度相称。
独立探索与生产运行隔离，不直接接入主系统；使用明确的测试数据、外部资源和运行边界。

完成条件是回答本轮问题并说明局限，结果可以是：

- 在已验证条件下可行；
- 能运行，但效果、成本或使用价值不满足要求；
- 被某个条件阻断；
- 证据不足，需要进一步探索。

验证可行可以作为独立交付，注明“尚未接入”。接入须在用户要求的范围内；以后接入前
重新核对依赖、数据条件和主系统现状，不把一次 pilot 当作普遍可靠的结论。

成功和失败探索均在交付中给出可追溯结论。到用户确认的记忆收尾时，集中保留目标、
条件、观察、原因、局限、重开条件、所属仓库与版本、数据 / 配置和证据入口。
记录探索分支的结论与有价值的尝试过程，不为每次命令重试追加一条决策。
未提交状态如实标明并保留必要差异；不编造 commit，也不为记录版本擅自提交。

## Integrate

把已验证能力接入现有系统时，完成以下与任务有关的结果：

- 业务逻辑有明确归属，依赖和接口符合现有边界；正式代码不依赖临时 demo。
- 输入、配置、错误语义与运行入口完整，不靠未说明的人工步骤维持成功。
- 新行为和受影响旧行为经过适当验证。
- 接入必需的局部整理当次完成，临时代码、重复入口和旧路径有明确去向。
- 允许保留有边界、有理由的技术债，在交付中交代影响与退出条件，
  经用户确认记忆更新后再沉淀到适当 owner，不强制每项小债务新建文档。

已接入不等于已提交或已部署，报告实际达到的状态。探针和 demo 可保留为示例、
基准或待接入资产；退役先确认代码、数据和环境可恢复，再按授权清理活跃目录。

## 验证责任

按行为风险和影响范围选检查，沿用项目已约定的核心回归入口，不默认全库重跑：

| 改动 | 重点 |
|---|---|
| 普通 UI 调整 | 实际展示、相关交互、必要构建与已有检查 |
| Bug 修复 | 复现与修复证据；高价值、易复发行为提炼为长期测试 |
| 新功能 | 新能力及直接受影响的旧行为 |
| 公共接口、权限、计费、共享数据 | 契约、调用方和关键业务链路 |
| Consolidate | 调整前需保留的行为基线、调整后的相关回归与边界 |

TDD 可用于规格明确或修复回归，不是统一前置步骤。
probe 观察现象，正式测试持续保护行为；Python 新测试通常为 `test_*.py`，
其他语言沿框架约定。既有 `_test_` 用途混杂时先盘点，迁移另行安排。
断言函数名或源码片段不能替代行为测试；结构约束本身才适合结构检查。

没有完整测试体系时如实列缺口，逐步把关键功能 / 契约映射到测试及执行命令。
映射归测试入口，memory 只导航。不能运行的外部或人工验收明确交代，
不将构建成功、probe 跑通或缺少失败日志当作完整验证。

## 日常整理、Consolidate 与 Rearchitect

日常整理服务当前修改，可包含命名、局部重复、分支和失效代码清理。
以目的和影响范围判断，不用行数、文件数或强制抽象数量衡量质量。
不要只因代码表面相似就抽成公共模块；看职责归属与是否一起变化。

在版本节点、累计多轮改动或显著结构信号出现时，主动检查：

- 同一规则是否分散维护；
- 普通需求是否反复牵连多个模块；
- 是否频繁跨越内部数据或依赖边界；
- 过渡实现是否长期并存，且权威路径不明确。

commit 数量只提醒检查，结构证据支持提案。提出问题、拟调整范围、预期收益和
验证方法，由用户决定是否及何时 Consolidate。必要的接入整理当次完成；
能独立开展、影响更多旧功能的整合单独安排。已有明确整合授权则直接完成。
用户暂缓后，在新证据或约定复查节点再提醒，避免每个小改动重复询问。

容量、可靠性、数据模型或开发成本使核心假设失效时，提出 Rearchitect 的证据、
局部替代方案与迁移范围，由用户决定。优先可验证的增量迁移，范围不必是整套系统。
重要边界能自动验证时采用依赖 / 契约 / 性能检查，但不预设任意阈值和未来架构。

## 工作收束与 Memory

用户要求的实现与相应验证完成后，主动询问工作是否收束、是否集中更新 memory。
节点可在 commit 前、commit 后或部署后，以约定交付范围为准。
用户已明确要求记忆编辑、维护或交接时按该授权执行，不重复确认。
用户暂缓、拒绝或自己整理时尊重决定；不通过写 handoff 绕过这个选择。

工作中不随小改动反复写 docs。确认后按完整过程更新相关 owner，复杂失败与排障
允许完整长文；活跃入口和历史证据分层。发现旧记忆不实先指出，列入收尾修正项。
具体写入可使用已安装的 `update-living-docs`；不可用时遵循项目记忆入口协议。
