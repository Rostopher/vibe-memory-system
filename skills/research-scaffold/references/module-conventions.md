# Research Module Conventions

适用于 `modules/` 或项目已有的研究实现目录。以下是职责示例，按需要选用，目录深度与语言遵循项目。

```text
modules/<module-name>/
  README.md                  可复用入口需要说明时再写
  probe_preview_inputs.py    局部观察 / 可行性验证，按需保留
  run_pipeline.py            正式运行入口
  tests/test_contract.py     也可放在项目统一 tests/ 中
  outputs/                  产物也可由配置指向统一存储
  logs/                     长任务或诊断需要时保留
```

## Explore 与 Integrate

- 技术路线未知时用隔离 demo；局部问题用 `probe_`；清晰修改直接实现。
  不规定所有任务先写 probe、测试或 PLAN 文件。
- 探索应回答具体问题，说明已测条件、结果、局限和证据不足之处。
  “可行，暂不接入”是有效结论；失败或条件受阻应能说明重开条件。
- 接入时确定正式模块和接口，补全实际调用路径、配置与错误处理，验证受影响的新旧行为。
  正式流程不依赖临时 demo。复用价值明确的 demo、示例或待接入实现可以保留。
- 当次完成接入必需的整理。可独立实施、会影响更多既有功能的整合提出具体方案，
  由用户决定 Consolidate 时机；不借小功能改动自行重写跨模块架构。

## 探针与正式测试

probe 用来观察和探索；正式测试用来持续发现约定被破坏。Python 新探针用 `probe_`，
正式测试用框架约定（通常 `test_*.py`）。既有 `_test_` 先判断实际用途，迁移另行安排。
不把 probe 改一个文件名就算补齐测试，也不强制采用 Test-Driven Development。

按影响范围运行项目核心检查及有关测试。在受影响的关键行为缺少保障时补有价值的覆盖，
并明确仍未验证的范围；无需在每次编辑后跑全库。

研究项目常需要保护这些契约：

- 数据 schema、主键与唯一性、连接基数、缺失值和异常输入的处理。
- 样本选择、变量定义、单位、权重、分母以及聚合口径。
- 固定小样本上的处理与分析结果，随机性 / 数值误差使用合理种子和容差。
- 面向用户或论文的关键运行路径，以及表图和上游结果的对应关系。

这里的软件回归测试与统计回归分析含义不同。代码仍能运行不保证研究含义保持不变；
比较结果前核对数据 / 样本 / 配置版本。基准或预期结果变化要解释原因，不能只更新期望值让测试通过。

成熟模块可在 README 或测试入口维护“关键行为 → 检查命令 → 覆盖缺口”的映射；
沿用已有测试入口，不为此新造重复清单。memory 只需导航到该入口。

## 数据、执行与证据

- Python 用 `pathlib.Path` 从脚本资源、项目配置或显式输入定位，避免隐式依赖 cwd。
  输出位置可配置，不强制产物与代码同目录；报告实际路径。
- 体量未知的大文件先预览 / 抽样，再选择全量、分块或流式读取，不无必要载入上下文。
- 日志、配置、Git revision、数据版本 / 哈希、环境、种子、指标与产物位置按复现需要保留。
  未提交代码说明 dirty 状态，并保存必要 patch 或快照，不能仅凭 commit 宣称可以复现。
- 长时间、付费 API 或高输出任务保留足够运行记录。失败、跳过、降级及不确定样本可见；
  不用静默 fallback 改变研究口径。已授权范围内的常规重试可继续。
- 在改变样本定义、研究假设或统计含义前确认该变化是否已获授权。
  当前代码与预期契约冲突时先核验，不把实现本身视为正确性的唯一证据。

可复用入口的说明以目标、输入 / 输出、命令、验证方法与当前限制为主，无需给每个临时脚本写一份文档。
运行记录随执行生成；项目级结论在工作收束时按已确认范围批量写入 memory。
