# Research Scaffold Contract

这份职责约定帮助定位内容，目录名可映射到现有项目布局。没有对应工作时不必预建空目录。

## 项目记忆根

新项目从当前 `vibe-memory-system` 安装完整 `memory-docs/`，入口为 `INDEX.md`。
已有项目以其实际入口和注册关系为准，例如 `docs/README.md`；协议升级与目录改名分别决定。
脚手架不维护另一套 docs 模板、全局 manifest 或固定 RUNBOOK 清单。

当前事实、状态、规则、目录映射与重要取舍归对应 memory owner。入口提供当前适用的结论及导航，
详细研究证据可以留在 notes、实验产物或可选账本中，通过链接连接。历史决策可以很长，
用当前视图、主题索引、稳定 ID 与替代关系保证可检索；不因年代久远就删除仍适用的决策。

## notes/ 与 ideas/

`notes/` 放经过理解的文献、方法、数据与 pipeline 分析。`notes/paper-reading/` 只是常见组织方式，
不需要预建所有分类。阅读记录区分作者 claim、自己的 inference 和已核实证据。
原始全文和 OCR 留在 `papers/`，正式论文文字进入 `manuscripts/`。

`ideas/` 保留尚待验证或暂缓的研究方向。按需要写清问题 / claim、相关证据、关键假设、
可能的失败原因、下一步如何减少不确定性。这里的最小验证可能是 probe 或实验，
不能据此宣称有了正式软件测试覆盖。失败想法仍有检索价值，保留停止原因与重开条件。

长篇排障、研究判断和失败过程可以完整保留。详细内容选一个 owner，memory 记录项目层面的
结论与入口；不要为了让多个文档看起来完整而复制多份。

## papers/ 与 repos/

`papers/` 放 PDF、metadata、OCR、图片及自动解析产物。人工阅读笔记另存；修改生成内容仅在
明确的元数据 / OCR 修正任务中进行，并确保重新生成时可追溯或重放修正。

`repos/` 放外部参考或复现代码，默认只读。记录来源与所用 revision；若需补丁，在已有授权内
保留可追溯修改。本项目实现放入自己的模块边界，不让正式流程依赖随手修改的参考副本。

## data/

可按需要划分 raw、interim、processed、external、dictionaries，或使用项目已有数据平台。
记录来源、版本、主键、样本口径、单位、缺失值和必要的转换关系，使结果可以复现。
大型数据可在仓库外管理，Git 中保留定位信息、配置、字典和适当的小样本。
按数据集的大小、许可、隐私和可复现需要决定版本化策略，不默认忽略整个 `data/`。

## modules/ 或已有实现目录

职责是可复用处理和分析流程、正式测试及必要的探索入口。现有 `src/`、`tests/` 等约定继续有效。
未知路线的 demo 可独立存在，不强制搬入每个正式模块。局部 probe、正式运行入口和测试
按用途组织，见 [module-conventions.md](module-conventions.md)。

代码、输入配置、数据版本、运行命令与产物应能相互追溯。日志和机器结果在执行时生成，
不需要等待 memory 收尾；这不意味着每次运行都要更新项目状态或决策。

## manuscripts/

放正式草稿、章节、附录、图表说明和回应材料。论文图表与其上游分析、数据、配置保持映射，
让展示结果的更新可以重现；避免手工复制数值后失去来源。不要把原始笔记或 OCR 当作正式写作。

## 更新边界

脚手架初始化或明确的目录维护按本次授权完成；后续 memory 在工作收束、确认范围后集中更新。
用户要求撰写的 notes / ideas / 研究报告照常交付，不以“等 memory 确认”为由延后。
也不把每次试错自动写成长文，或通过换目录名绕过用户对记忆沉淀时机的约定。
