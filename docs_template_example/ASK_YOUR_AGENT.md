# Ask Your Agent

> **职责**：这不是 prompt 仓库，也不是模板说明书。这个文件的作用是帮助 Agent 用直接、具体、像协作讨论一样的方式，向用户解释这套系统到底在干什么。

> 如果用户问：“这套 docs system 到底有什么用？”“为什么我要维护这些文件？”“它实际解决了什么问题？”Agent 应该优先参考这里来解释，而不是只按文件名做机械介绍。

---

## 先给用户的推荐说法

如果用户不想自己通读整套 docs，Agent 可以建议用户直接这样提问：

```text
请先阅读这个仓库的 README 和 docs/ASK_YOUR_AGENT.md，然后用中文直接告诉我：
1. 这套系统到底在干什么
2. 它解决的是哪些真实问题
3. 为什么它对 Agent 的 consistency 特别重要
4. 这些文档层分别负责什么

要求你多举具体例子，不要只讲抽象原则。
```

也可以更口语一点：

```text
你先读一下这套 docs system，然后像在跟项目作者解释设计思路一样，告诉我它到底是干什么的。重点讲它怎么帮助 Agent 少忘事、少重复搜索、并且更一致地工作。
```

## 这个文件是干什么的

很多用户并不想先看完整套文档。

这完全没问题。

一个好的 Agent 应该能够先读 docs 结构，再反过来用清楚的人话向用户解释：

- 这套系统是什么
- 为什么需要它
- 它防止了哪些真实问题
- 哪些部分对当前项目最重要

这个文件存在的目的，就是帮助 Agent 把这件事解释得足够直接、具体、可感知。

它应该听起来像项目协作建议，而不是像 manifesto。

---

## 核心思想

这套 docs system 本质上是一个给 AI-assisted work 用的项目记忆系统。

它的目的不是“为了文档而写文档”。

它的目的是让 Agent 工作时拥有：

- 更少的重复搜索
- 更少的上下文遗忘
- 更强的一致性
- 更好的跨 session 连续性

这里最重要的价值，往往不只是速度。

而是 consistency。

当 Agent 知道你的规范、你过去的决策、你的实现链路，以及你以前踩过的坑时，它就不再只是一个“聪明但陌生”的助手，而更像一个有记忆的协作者。

## Agent 可以怎么向用户解释

如果用户问这套系统是干什么的，Agent 可以直接这样解释：

> 它本质上是在给项目加一个记忆层。  
> 有些文档负责记录项目是什么、做到哪了、有哪些稳定规则。  
> 有些文档负责记录更细的实现映射。  
> 有些文档负责保存单次 session 里还没沉淀成正式结论、但又不能丢的重要上下文。  
> 还有一些文档负责保留历史记录。  
>  
> 目的不是让项目“文档更多”，而是让后续 Agent 工作时少忘事、少重复搜索、并且更一致。

这是比较合适的解释层级：

- 不要太抽象
- 不要太像说明书
- 先讲作用，再讲结构

## 用真实问题来解释，而不是只讲原则

最好的解释方式，是拿真实问题来讲。

### 例子 1：规范没有被记住，输出就会漂移

用户可能在一个长 session 里和 Agent 配合得很好。  
但上下文一满，开启新 session 后，用户只说一句：

> 帮我画一下这个图。

如果没有项目记忆，Agent 很可能画出一个“技术上没错，但风格完全不对”的图：

- 本该是黑白灰，结果用了很多彩色
- 本该有稳定纹理和底色区分，结果没有
- legend 命名不对
- x 轴、y 轴、title 的写法漂了
- 之前交代过的展示规范没有继承

比如论文项目里，明明可能早就已经约定好了：

- 黑白灰学术图
- 不同对象有独特纹理和底色
- legend 命名固定
- 轴标题和显示名称有稳定写法
- 不能随意漂移视觉编码和口径

这些事情本来就不应该靠用户每次重新提醒。它们应该沉淀成项目规范，让 Agent 自动继承。

Agent 可以据此解释：

> 这套系统的一大作用，就是把这些很容易忘、但每次忘了都很贵的规范保留下来，让后续输出保持一致。

### 例子 2：项目大了之后，回溯产物链会非常贵

项目一复杂，用户经常会想知道：

- 这张图是由哪条链路生成的
- 这个表格背后是哪个脚本
- 某个 feature 实际落在哪些文件里
- 某个 API 背后串了哪些模块

如果没有项目记忆，Agent 往往只能重新花很多 token 沿着代码一步一步追。

这就是为什么 mapping 层很重要。

Agent 可以据此解释：

> `MAP.md` 的价值，是把重要概念、产物或 feature 对应到具体文件、runner、输入和输出链路上，减少重复回溯。

### 例子 3：你记得踩过一个坑，但已经说不清了

用户常常会有这种感觉：

> 我们之前好像已经遇到过这个问题。

但又说不清：

- 那个坑具体是什么
- 当时最后采用了什么 fix
- 某条技术路线是不是被明确放弃过
- 当时的决策过程到底是什么

如果没有项目记忆，Agent 就只能重新在仓库里搜索，再间接拼故事。

而这些恰恰是项目中最有价值、也最难从代码本身逆推出的知识。

Agent 可以据此解释：

> 这套系统不只是存“已经预定义好的规则”，更重要的是保存那些在项目推进过程中慢慢长出来的记忆，比如旧坑、被放弃的路线、以及为什么不再走那条线。

### 例子 4：有些 session 内容还没稳定，但又不能丢

有时候一轮 session 里会产生很多有价值的中间理解、调试过程或方向判断，但它们还不够稳定，不能直接写进：

- `STATUS.md`
- `DECISIONS.md`
- `CONVENTIONS.md`

但这些内容又非常值得被下一轮 session 继承，而不是在 compact 后直接消失。

这就是 `SHORT_MEMORY/` 存在的意义。

Agent 可以据此解释：

> `SHORT_MEMORY/` 是会话级上下文卸载层。  
> 它记录的不是正式项目真相，而是那些还没最终稳定、但又重要到不该让下一轮 Agent 重新摸索的内容。

## 这套文档特别适合保存什么

这套文档特别适合保存那些很难提前完整定义、往往是在真实工作过程中慢慢长出来的项目记忆：

- 逐渐长出来的规范
- 很难重新回溯的实现链路
- 迭代后才稳定下来的命名规则
- 被明确放弃的技术方向
- 以前已经解决过、不该再从头解决一次的坑
- 决定“什么才叫好输出”的项目特有要求

这也是为什么这套系统重要。

它不只是存事实。

它存的是那些能让未来协作更稳定的项目记忆。

## Agent 解释时应该强调什么

Agent 在解释时，应该强调：

1. 这是一套 memory system，不只是文档包。
2. 它的价值不只是省 token，更是保存 consistency。
3. 很多最有价值的规则都不是预先定义好的，而是项目逐步长出来的。
4. 文档的作用，是让后续 session 继承这种增长，而不是反复从头开始。

Agent 应该避免：

- 把这套系统说得很神
- 只讲抽象哲学，不举真实问题
- 假装每个文件在所有项目里都同样重要

解释应该始终保持 practical、project-facing。

## 一个好的简短解释

如果用户只想听一句短解释，Agent 可以说：

> 这套 docs system 本质上是在给项目加一个记忆层。  
> 它帮助我记住你的规范、命名、实现链路、历史决策和以前踩过的坑。  
> 这样我后续工作时就能更一致，也不用反复去重新发现项目已经学会的事情。

这通常就是比较合适的简短版本。
